# COM7 hardware bring-up — 2026-10-31

Hardware: ESP32-D0WD-V3 rev 3.1, 4 MB flash, one MLX90393 on
MUX CH0 and OLED on CH5. USB bridge: CH340, COM7.

## Observed on the bench

- User reported PWR LED extinguishing when external power wiring was
  attached. User corrected the connection; exact wiring fault was not
  identified remotely.
- Manual BOOT + EN while esptool was already waiting connected reliably.
  Automatic RTS reset did not reliably start the application. A manual EN
  press with BOOT released produced readable boot logs.
- Original bootloader, partition table and application passed esptool
  digest verification. Original application was backed up to
  `.pio/bench-backup/firmware-original.bin` before diagnostic flashing.
- Standalone `board_bringup` firmware ran on the bare board and then
  scanned the assembled circuit at 100 kHz, four consecutive times:
  MUX `0x70`; CH0 `0x0C`; CH5 `0x3C`; other channels empty.
- Restored main firmware at 400 kHz booted, detected the OLED as SSD1306,
  and started AP `SCRATCHSOR-9BD8`, HTTP and WebSocket services. User
  confirmed visible text on the OLED after manual EN reset.
- That main firmware did not detect the sensor and failed to allocate its
  600-frame recorder buffer. These were actual boot-log failures.

## Changes prepared for verification

- Shared I2C clock 100 kHz, including U8g2's per-transfer clock setting.
- Recorder capacity 128 frames; UI and API examples updated to match.
- Startup diagnostics report allocated recorder size and the first valid
  acquisition frame. Recording cannot report itself active without a buffer.
- Default upload/monitor port COM7. Standalone scanner remains available
  under the explicitly selected `board_bringup` environment.
- User requested Wi-Fi name/password equality and web configuration of a
  constrained two-magnet gap experiment. Added the Settings form, persisted
  experiment identity/baseline, stored calibration inspection and OLED gap
  output gated on validation. See [workflow](magnet-gap.md).
- Host verification: 5 gap-policy + 10 calibration-math + 12 signal-processing
  tests passed with Zig C++; JavaScript syntax check passed. Local UI preview
  verified Settings and Calibration rendering without console errors.

## Post-change hardware verification

- Flashed application (976112 bytes) and LittleFS (1441792 bytes) on COM7;
  esptool verified both hashes.
- Manual EN reset with BOOT released booted the updated main application.
- Boot log: `Web UI index ready: 2117 bytes`; shared bus at 100000 Hz;
  MUX CH0 `0x0C`, CH5 `0x3C`; OLED detected as SSD1306.
- `Recorder ready: 128 frames, 30208 bytes` replaced the allocation failure.
- `Magnetometers online: 1/4` and `First acquisition frame: 1/4 valid sensors
  (seq 2)` confirmed actual sensor acquisition in the main application.
- AP `SCRATCHSOR-9BD8`, HTTP :80 and WebSocket :81 started. User confirmed
  the new OLED screen is visible and confirmed the magnet-gap Settings page
  over Wi-Fi with the matching SSID/password.
- Continued monitoring found a short burst of sensor I2C errors/recoveries
  around uptime 20–23 seconds. A follow-up driver change separates MLX command
  writes and response reads with STOPs, matching the reference driver's I2C
  exchange. Follow-up firmware build/flash and 30-second health counters are
  the verification loop; stability is not inferred from boot detection alone.
- STOP-separated commands removed the observed low-level repeated-START
  errors in the next monitoring window, but health counters still showed
  111, 201 and 276 acquisition errors at 30/60/90 seconds. A full 1024-byte
  OLED framebuffer requires at least 92 ms at 100 kHz while the sensor lock
  timeout was only 50 ms. Increased lock wait to 150 ms; verification pending.

## Final stability check

- Follow-up application (976048 bytes) was fully written. The initial
  connection ended during its automatic verification; a separate esptool
  `verify_flash` completed with `verify OK (digest matched)`.
- With 150 ms bus lock wait, the first valid sensor frame was seq 1.
- At approximately 30 seconds: `1/4 valid, 10.0 Hz, ok=287 err=0`.
- At approximately 60 seconds: `1/4 valid, 10.0 Hz, ok=587 err=0`.
- Final captured snapshot at approximately 90 seconds: `1/4 valid,
  10.0 Hz, ok=887 err=0`.
- This bounded real-board check passed with the OLED running. It does not
  claim long-duration stability or calibrated magnet-gap accuracy.
- Raw local evidence: `.pio/bench-backup/boot-lock-150ms.log`.

Physical magnet-gap calibration accuracy and recorder/export operations remain
untested; no model was fabricated or calibration fixture acknowledged for the user.
